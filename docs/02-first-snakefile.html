2  A first Snakefile

Start in examples/01-first-rules. It contains two R scripts — sim.R, which runs the simulation for one method, and figure.R, which turns simulation output into a figure — and a file called Snakefile.

By hand, building the figure means running three commands in the right order:

Rscript sim.R naive rds/sim-naive.rds
Rscript sim.R split rds/sim-split.rds
Rscript figure.R out/figure1.pdf rds/sim-naive.rds rds/sim-split.rds

That is not hard. It is just something you have to remember, and remember again every time you change one of the scripts, and remember correctly — because nothing stops you from rebuilding the figure without rerunning the simulation.

2.1 Rules

A Snakefile is a list of rules. A rule says: here are the files I need, here is the file I produce, and here is the command that gets from one to the other.

Snakefile
rule all:
    input:
        "out/figure1.pdf"

rule sim_naive:
    input:
        "sim.R"
    output:
        "rds/sim-naive.rds"
    shell:
        "Rscript sim.R naive {output}"

rule sim_split:
    input:
        "sim.R"
    output:
        "rds/sim-split.rds"
    shell:
        "Rscript sim.R split {output}"

rule figure:
    input:
        script = "figure.R",
        rds = ["rds/sim-naive.rds", "rds/sim-split.rds"]
    output:
        "out/figure1.pdf"
    shell:
        "Rscript {input.script} {output} {input.rds}"

Read rule sim_naive as a sentence: to make rds/sim-naive.rds, given sim.R, run Rscript sim.R naive rds/sim-naive.rds.

A few mechanics:

  • {output} and {input} are substituted into the shell command. You write the filename once, in the output: block, and refer to it after that. This is not just brevity — it makes it impossible for the rule to declare one file and write a different one.
  • Inputs can be named, as in rule figure, where input.script and input.rds are referred to separately in the command. Without names, {input} expands to all of them, space-separated, in order.
  • Indentation matters, as in Python. Use four spaces and stay consistent.
  • sim.R is listed as an input, even though it is code rather than data. This is important. It is what makes “the script changed” a reason to rerun.

2.2 rule all

rule all is different. It has no output and no command — only inputs. It exists because of a rule Snakemake follows strictly:

Snakemake builds the first rule in the file, and whatever that rule needs.

So rule all is where you list the things you actually want to exist at the end. Everything else gets built because something in that list, directly or indirectly, depends on it. Anything not reachable from it is simply not part of a plain snakemake run — though you can still ask for it by name, which is the next section. By convention this is named rule all, but what matters is that it is first.

2.3 The dependency graph

From those four rules Snakemake works out the order for itself. Nothing in the file says the simulations come before the figure; it deduces that from the fact that rule figure needs files that rule sim_naive and rule sim_split produce.

This is a directed acyclic graph (DAG). Two consequences worth internalizing early: anything with no path between the nodes can run at the same time (Chapter 5), and a cycle is an error rather than an infinite loop (it won’t run).

2.5 Doing nothing, quickly

Run it again:

$ snakemake --cores 2
Nothing to be done (all requested files are present and up to date).

This is the point of the exercise. Ask for the figure a hundred more times and you will get that message a hundred times. Now delete the figure and ask again:

2.6 What counts as out of date

Here is where Snakemake differs from make, and from most people’s expectations.

make asks one question: is the input newer than the output? If so, rebuild.

Snakemake asks two, and needs both answers to be yes. It keeps a record of every output it has ever made — in a directory called .snakemake/ — including a SHA-256 checksum of each input that went into it. A job is out of date when

  1. an input’s timestamp is newer than the output’s, and
  2. that input’s contents differ from what was recorded.

The timestamp is the gate and the checksum is the confirmation. So:

$ touch scripts/sim.R && snakemake -n
Nothing to be done (all requested files are present and up to date).

Touching a file does not trigger a rebuild, because the contents did not change. Change one character of sim.R, though, and everything downstream of it goes:

$ echo '## a real edit' >> scripts/sim.R && snakemake -n
Job stats:
job           count
----------  -------
all               1
figure1           1
manuscript        1
sim              18
table1            1
total            22

(That transcript comes from the larger example of Chapter 7, which is why there are 22 jobs rather than 4.)

Content is not the only trigger. Snakemake also stores the shell command and the parameters used for each output, so editing a rule’s command — not just the script it calls — makes the affected outputs stale too. Chapter 9 covers how to inspect and override all of this.

WarningThe timestamp really is a gate

Because the check is an and, a changed file whose timestamp is not newer than the output is invisible: Snakemake never gets as far as comparing the checksum. You will not produce that situation by editing a file — editing sets the timestamp to now — but you can arrive at it by other routes, because several common tools preserve timestamps deliberately:

cp -p old/sim.R scripts/sim.R      # -p preserves the original mtime
rsync -a backup/ .              # -a implies -t
tar xf archive.tar              # restores the archived mtimes

Restore a script from a backup or an archive that way and the pipeline can sit there insisting everything is up to date. If you have moved files around by any means other than editing them, touch the ones you restored, or force the issue with snakemake -R (Chapter 9).

NoteDeleting .snakemake/ is safe

It is a cache of metadata, not results. Delete it and the next run rebuilds everything, because Snakemake no longer has any record of how the existing files were made. Add it to .gitignore and otherwise ignore it.

2.7 Building one thing

You can also name a target directly, which is invaluable when you are developing and want to check one piece:

snakemake --cores 1 rds/sim-naive.rds

Snakemake finds the rule that can produce that file, builds whatever it needs, and stops. You can also name a rule — snakemake --cores 1 figure — which asks for that rule’s outputs.

Neither form cares about rule all. A rule that nothing in rule all reaches is still perfectly buildable by naming it, which is how a half-finished piece of a project gets exercised before it is wired into the paper.

The one restriction is that a rule whose output contains a wildcard cannot be named — Snakemake would have no way to know which values you meant:

$ snakemake --cores 1 sim
WorkflowError:
Target rules may not contain wildcards. Please specify concrete files or a rule
without wildcards at the command line …

Name a file instead, and the wildcards come from the filename as usual:

snakemake --cores 1 rds/200/sim/n50_rho0_naive.rds

2.8 One Snakefile, one project

Before going further, it is worth being explicit about what a “project” is here, because every example in this book is one and your own work should be too.

examples/01-first-rules is a complete, self-contained project. Copy that directory anywhere on your disk and everything still works — it has no dependency on the rest of this repository. The same is true of each of the other four. They are laid out side by side for convenience, but each is a miniature of a real repository: one paper, one analysis, one thing.

The layout that scales from these examples up to a real methods paper is:

the shape of a project
my-project/
  Snakefile          <- the map: every rule, in one file, at the root
  config.yaml        <- the settings (chapter 4)
  scripts/              <- the scripts the rules call
  rds/               <- computed results
  out/               <- figures and tables

Three of those deserve to be stated as rules rather than suggestions.

One Snakefile, at the root. Not one per subdirectory. The Snakefile is the only place that describes how the pieces of the project fit together, so a newcomer — a coauthor, a reviewer, you in a year — has exactly one file to open to find out what this project builds and what it builds it from. Snakemake does let you split rules across files with include:, and that is worth reaching for once a single file becomes genuinely unwieldy, but the default should be one file you can read top to bottom.

rds/ holds what the pipeline computes. Simulation output, fitted models, cleaned data — the objects that took time to produce and that everything else is derived from. They are serialized R objects, hence the name; use whatever name you like, but use one directory.

out/ holds what a human looks at. Figures and tables: the things that end up in the manuscript or the report.

The reason to split these rather than pile everything into one results/ folder is that the two halves behave completely differently. rds/ is expensive, is reused across a paper and a talk and a grant renewal, and may take days to regenerate — it is the thing worth backing up and worth sending to a coauthor. out/ is cheap: delete it and snakemake puts it back in seconds, from the contents of rds/. Once they are separate directories you can treat them differently, and Chapter 10 does exactly that.

The corollary is that anything not in rds/ or out/ is either code, settings, or something a human wrote. That is a useful thing to be able to say about a directory — and it is what makes the next rule easy to apply.

Neither rds/ nor out/ is tracked by git. Not because they are large, or binary, or likely to go stale — those are consequences, and reasoning from them means relitigating the question for every new kind of file. The rule is simpler than that:

Git is for source, not output.

Source is what a person wrote: the scripts, the Snakefile, the config, the .tex files. Everything in rds/ and out/ was produced by running that source, so none of it belongs in the repository.

.gitignore
rds/
out/
.snakemake/

Stated that way it also settles the case people otherwise talk themselves out of. A figure is small and it is genuinely convenient to look at a PDF on GitHub — but size has nothing to do with whether something is source, and out/figure1.pdf is as much an output as a four hundred megabyte .rds. If you want to see the figures, run snakemake. It takes seconds, and what you get is guaranteed to match the code you are looking at.

The one thing this costs you is that a fresh clone cannot show anybody a result until it has been rebuilt. When the rebuild takes days rather than seconds that is a real cost, and Chapter 10 deals with it — by sharing rds/ outside of git, not by committing it.

2.9 Try it

  1. Delete out/ and rebuild. Time it. Then delete rds/ as well and compare.
  2. Change the n <- 100 line in sim.R to n <- 200 and run snakemake -n. Which jobs are planned, and why?
  3. Add a line to rule all asking for out/nonexistent.pdf and run snakemake -n. Read the error carefully — you will see it again.
