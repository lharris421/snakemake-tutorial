8  A data analysis pipeline

Most biostatisticians spend more time on analyses than on simulation studies, and the shape of the work is different: instead of a fan-out over a parameter grid, a mostly linear chain from a file someone emailed you to a report you send back. The Snakemake ideas transfer directly, and one of them — the report as a rule — addresses a problem specific to this kind of work.

Move to examples/05-analysis. It is a small randomized trial: 200 participants, two arms, FEV1 measured at baseline and week 12.

8.1 The pipeline

$ snakemake --cores 4

8.2 Raw data is read-only

The first rule reads data/trial.csv and never writes to it. That is not a Snakemake requirement; it is the convention that makes everything else work, and it deserves stating plainly: the raw file stays exactly as it arrived. Every correction, exclusion and recoding happens in code, downstream, where it can be read and argued with.

Note also what is not in the Snakefile. data/make-raw-data.R, which generated the CSV for this example, is not a rule. If it were, Snakemake would treat the raw data as something it could regenerate, and would do so — silently discarding the real file the moment it decided it was out of date. Anything you cannot afford to lose should be an input to your pipeline and never an output of it.

8.3 Cleaning once

scripts/clean.R (excerpt)
raw <- read.csv(opt$infile, stringsAsFactors = FALSE)
log_step <- function(d, msg) {
  cat(sprintf("%-45s n = %d\n", msg, nrow(d)))
  invisible(d)
}
log_step(raw, "raw file")

d <- raw[!duplicated(raw$patient_id), ]
log_step(d, "after dropping duplicate patient records")

## Sex arrives as F/f/female/Female/M/male/Male
d$sex <- ifelse(toupper(substr(d$sex, 1, 1)) == "F", "Female", "Male")

## Ages over 120 are data entry errors, not centenarians
d$age[d$age > 120] <- NA
log_step(d[!is.na(d$age), ], "with a usable age")

d$visit_date <- as.Date(d$visit_date, format = "%m/%d/%Y")
d$arm <- factor(d$arm, levels = arm_levels)
d$smoker <- factor(d$smoker, levels = c("Never", "Former", "Current"))
d$change <- d$fev1_wk12 - d$fev1_base

## The primary analysis needs a week 12 measurement
d <- d[!is.na(d$change), ]
log_step(d, "with a week 12 measurement (analysis set)")

Every decision about the data is in this one script, and it announces each one:

$ cat logs/clean.log
raw file                                      n = 201
after dropping duplicate patient records      n = 200
with a usable age                             n = 199
with a week 12 measurement (analysis set)     n = 191
wrote rds/analysis.rds

That is the participant flow for your CONSORT diagram, produced as a side effect of the pipeline rather than counted by hand, and regenerated every time the data changes. When the coordinator sends an updated export in June, snakemake reruns everything downstream and this log tells you immediately whether the exclusions still look the way they did in March.

The alternative — each analysis script starting with its own read.csv() and its own quiet decisions about who to drop — is how two tables in the same report end up with different denominators.

8.4 The report is a view, not a computation

Here is the part specific to analysis work. It is normal to put everything in one .qmd file: read the data, fit the models, print the tables, write the text. It works, and it has two failure modes that get worse as the project grows.

The first is time. A report that refits everything takes as long as the slowest model every time you fix a typo, and the temptation is to start caching chunks, at which point you no longer know whether the numbers in the output correspond to the code in the file.

The second is scope. Rendering becomes all-or-nothing — you cannot ask for just the models — and the results exist only inside the rendered HTML, so the next project that needs them starts by copying and pasting.

Splitting it fixes both. The scripts compute and save; the report reads and displays:

report.qmd (excerpt)
```{r}
#| include: false
library(knitr)
analysis <- readRDS("rds/analysis.rds")
tab1 <- readRDS("rds/table1.rds")
models <- readRDS("rds/models.rds")
eff <- models$effects
```

The report does no computing of its own. It reads the objects the pipeline
produced and displays them, so that rendering it can never quietly change a
result.
Snakefile (excerpt)
## Listing every object the report reads is what makes the report trustworthy:
## it cannot be rendered against a stale table or a figure from last month.
rule report:
    input:
        qmd = "report.qmd",
        analysis = "rds/analysis.rds",
        models = "rds/models.rds",
        table1 = "rds/table1.rds",
        figure1 = "out/figure1.png"
    output:
        "report.html"
    log:
        "logs/report.log"
    shell:
        "quarto render {input.qmd} --to html > {log} 2>&1"

Listing each object the report reads is what makes the report trustworthy. Rendering it cannot use a stale table, because Snakemake will rebuild the table first. And the models are in rds/models.rds, so the manuscript you write next year can load them without rerunning anything.

Everything the report needs to say in prose comes through inline R:

report.qmd (excerpt)
The estimated treatment effect is
`r sprintf("%.3f L (95%% CI %.3f to %.3f)", eff$estimate[eff$model == "adjusted"], eff$lower[eff$model == "adjusted"], eff$upper[eff$model == "adjusted"])`
in the adjusted model, and is insensitive to which covariates are included.

so the sentence and the table cannot disagree.

8.5 Models as data

scripts/model.R (excerpt)
specs <- list(
  unadjusted = change ~ arm,
  adjusted   = change ~ arm + age + sex + fev1_base,
  full       = change ~ arm + age + sex + bmi + smoker + fev1_base
)

fits <- lapply(specs, function(f) lm(f, data = d))

## Pull the treatment effect out of each fit into one tidy data frame
effects <- do.call(rbind, lapply(names(fits), function(nm) {
  fit <- fits[[nm]]
  ci <- confint(fit)["armTreatment", ]
  data.frame(model = nm,
             estimate = unname(coef(fit)["armTreatment"]),
             lower = ci[1], upper = ci[2],
             p = summary(fit)$coefficients["armTreatment", "Pr(>|t|)"],
             n = length(residuals(fit)),
             row.names = NULL)
}))

Two things worth copying here. The model specifications are a named list, so adding a sensitivity analysis means adding one line and touching nothing else. And the script saves both the fitted objects and a tidy data frame of the estimand — the first for anything you did not anticipate, the second so the report does not need to know how to dig a confidence interval out of an lm.

$ cat logs/model.log

8.6 When the data changes

Which it will, usually the week after you send the report. Drop in the new export and:

snakemake --cores 4

Cleaning reruns, the models refit, Table 1 and the figure regenerate, the report re-renders, and the participant-flow log tells you what changed about the analysis set. The work of a data update goes from an afternoon of retracing your steps to one command and a careful look at one log file.

8.7 Try it

  1. Edit a value in data/trial.csv and run snakemake -n. What reruns?
  2. Add a rule producing a subgroup analysis by smoking status, and show it in the report.
  3. Delete rds/analysis.rds but not the models. What does Snakemake do, and is that what you expected?
